# 附录二十三：Git

> 这个附录介绍 Git 的基本用法。Git 是一个版本管理工具，可以记录文件每次的变化，让你随时回到之前的某个版本。写论文、写代码、写任何文档，用 Git 都能省去“定稿-最终版-最终版2-打死也不改版”这种烦恼。

## 23.1 为什么要用 Git

写论文的时候，你大概经历过这种事：

```
论文_初稿.docx
论文_修改1.docx
论文_修改2.docx
论文_导师反馈.docx
论文_最终版.docx
论文_最终版_真的不改了.docx
```

然后导师说：“我觉得第一版那个结构更好，改回来吧。” 你对着十几个文件翻来翻去找，又怕删错东西。

Git 就是解决这个问题的。它能记录每一次修改，任何时候都可以回到任意一个历史版本。你永远只有一个文件，不用再建一堆副本。

**Git 的好处**：
- 每次修改都有记录，可以随时查看改了什么
- 想回到之前的任意版本，一条命令搞定
- 可以开“分支”做实验性修改，不满意直接丢掉，不影响主版本
- 多人协作时不会互相覆盖

## 23.2 安装 Git

**Windows**：访问 [`git-scm.com/download/win`](https://git-scm.com/install/windows)，下载安装包，一路默认选项即可。安装完后在开始菜单搜索“Git Bash”，打开看到一个命令行窗口，说明安装成功。

**macOS**：打开终端，输入 `git --version`，如果没有安装，系统会自动提示安装 Command Line Tools，按提示操作即可。

**Linux（Ubuntu/Debian）**：`sudo apt install git`

安装完成后，在命令行（Windows 用 Git Bash，macOS/Linux 用终端）输入以下命令设置你的名字和邮箱（随便填，只是用来标记谁改的）：

```bash
git config --global user.name "你的名字"
git config --global user.email "你的邮箱"
```

## 23.3 初始化仓库（git init）

Git 会把一个文件夹变成“仓库”（repository），所有版本记录都保存在这个文件夹里。

**操作方法**：

1. 在文件资源管理器里，为你的论文单独建一个文件夹，比如 `D:\thesis`
2. 右键点击文件夹 → 选择“Git Bash Here”（如果装了 Git）
3. 在命令行输入：

```bash
git init
```

你会看到类似 `Initialized empty Git repository in D:/thesis/.git/` 的提示。这个 `.git` 文件夹就是 Git 存放所有历史记录的地方。**不要动它**。

之后你在 `thesis` 文件夹里做的所有修改，Git 都能帮你记录下来。

## 23.4 第一次提交（First Commit）

“提交”（commit）就是给当前所有文件拍一张快照，存进 Git 的历史记录里。

**场景**：你刚写完论文第一章，想保存一下。

**操作步骤**：

1. 把文件添加到“暂存区”（stage）——相当于告诉 Git“这些文件我要保存”：

```bash
git add 第一章.docx
```

如果想一次性添加当前文件夹里的所有文件：

```bash
git add .
```

2. 提交并写一条说明（用 `-m` 加一段话，说明这次改了什么）：

```bash
git commit -m "完成第一章初稿"
```

现在你的论文第一章就有了第一个版本记录。以后每次写到关键节点，都执行一次 `git add .` + `git commit -m "说明"`。

**查看历史记录**：

```bash
git log
```

会列出所有提交记录，每条记录有一串 hash 值（如 `a1b2c3d`）、作者、时间和提交说明。

## 23.5 查看修改状态

随时输入以下命令，可以知道当前文件夹里哪些文件被修改了、哪些还没有提交：

```bash
git status
```

它会告诉你：
- 红色文件：被修改了但还没 `add`
- 绿色文件：已经 `add` 了但还没 `commit`
- 干净的工作区：所有修改都已提交

养成经常敲 `git status` 的习惯，你永远不会搞不清自己改到哪了。

## 23.6 分支（Branch）：做实验不害怕

分支是 Git 最核心的功能。你可以把它理解成“平行宇宙”。

**场景**：导师说“你试试把第三章的结构调整一下，但我不确定效果好不好，你先改着看看。” 你不想破坏现有的版本，但又想尝试新方案。

**操作方法**：

1. 从当前版本开一个新分支：

```bash
git branch 实验性修改
```

这条命令创建了一个叫“实验性修改”的分支，它和当前主分支（master/main）的内容完全一样。

2. 切换到新分支：

```bash
git checkout 实验性修改
```

或者一步到位（创建并切换）：

```bash
git checkout -b 实验性修改
```

3. 在新分支里随便改，随便提交。改得乱七八糟也不怕，因为不影响主分支。

**切回主分支**：

```bash
git checkout master   # 或者 main
```

你的文件会变回主分支的样子，所有实验性修改都暂时“藏”在实验性修改分支里。

**查看所有分支**：

```bash
git branch
```

带 `*` 的是当前所在分支。

## 23.7 合并（Merge）：把实验成果收回来

实验性修改效果不错，导师也满意，想把改动合并回主分支。

**操作方法**：

1. 先切回主分支：

```bash
git checkout master
```

2. 执行合并：

```bash
git merge 实验性修改
```

Git 会把“实验性修改”分支里的所有改动合并到主分支。如果两个分支改的是同一个文件的同一行，Git 会提示**冲突（conflict）**，需要手动解决——打开冲突文件，Git 会在文件里用 `<<<<<<<`、`=======`、`>>>>>>>` 标出冲突的地方，你选择保留哪个版本，删除标记符号，然后保存、`add`、`commit`。

**如果实验失败了**：直接删掉分支就行，主分支不受影响。

```bash
git branch -d 实验性修改
```

## 23.8 实际场景：导师帮你改了论文

导师说“我帮你改了一下第三章”，然后把修改后的文件发给你。你用新文件覆盖了旧的。怎么用 Git 看出导师改了哪里？

**操作方法**：

1. 在覆盖之前，先确保所有修改都已提交（`git status` 应该是干净的）。
2. 用导师发来的新文件覆盖旧文件。
3. 用 `git diff` 查看差异：

```bash
git diff
```

这会显示每一行发生了什么变化——绿色是新增的，红色是删除的。

4. 确认无误后提交：

```bash
git add .
git commit -m "导师修改第三章"
```

**如果导师改了好几版**：每次收到新版本，都重复上面的步骤。Git 会帮你保留每一版的改动记录，随时可以回溯。

## 23.9 回到过去：后悔了怎么办

**场景**：你改了三天，发现方向不对，想回到三天前的版本。

1. 查看历史记录，找到想回去的那个版本的 hash 值（前几位就行）：

```bash
git log
```

2. 回到那个版本：

```bash
git checkout a1b2c3d   # 用你查到的 hash 替换
```

你的文件就变回那个版本的样子了。如果想在此基础上继续修改，开一个新分支。

**更彻底的“回到过去”**（丢弃所有后续修改）：

```bash
git reset --hard a1b2c3d
```

**⚠️ 警告**：`git reset --hard` 会永久删除后续的修改，用之前想清楚。

## 23.10 几个实用命令速查

| 命令 | 作用 |
|------|------|
| `git init` | 初始化仓库 |
| `git add 文件名` | 添加文件到暂存区 |
| `git add .` | 添加所有修改到暂存区 |
| `git commit -m "说明"` | 提交 |
| `git status` | 查看当前状态 |
| `git log` | 查看提交历史 |
| `git log --oneline` | 简洁版历史（一行一条） |
| `git diff` | 查看未暂存的修改 |
| `git diff --staged` | 查看已暂存但未提交的修改 |
| `git branch` | 查看分支列表 |
| `git branch 分支名` | 创建分支 |
| `git checkout 分支名` | 切换分支 |
| `git checkout -b 分支名` | 创建并切换分支 |
| `git merge 分支名` | 合并分支到当前分支 |
| `git branch -d 分支名` | 删除分支 |
| `git checkout hash值` | 切换到某个历史版本 |
| `git reset --hard hash值` | 彻底回到某个历史版本 |


# 补充阅读

> 以下内容涉及 Git 的更深入用法，用到了再回来看。

## 补充1：`.gitignore` 文件

有些文件不想被 Git 跟踪，比如编译生成的临时文件、系统缓存、大文件等。在仓库根目录创建一个 `.gitignore` 文件，里面写上要忽略的文件名或规则：

```
*.tmp
*.log
.DS_Store
node_modules/
```

Git 会自动忽略这些文件，不会出现在 `git status` 里。

## 补充2：修改上一次提交

刚提交完发现写错了说明，或者漏了一个文件：

```bash
git commit --amend -m "新的提交说明"
```

这会修改最近一次提交，不会产生新的提交记录。

## 补充3：暂存未完成的工作（stash）

你改到一半，需要紧急切到另一个分支修 Bug，但当前修改还没到可以提交的程度：

```bash
git stash          # 暂存当前修改，工作区变干净
git checkout 其他分支
# ... 修完 Bug ...
git checkout 原分支
git stash pop      # 恢复之前的修改
```
